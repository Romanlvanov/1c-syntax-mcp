# План улучшения поиска в 1c-syntax-mcp

Аудит проведён на реальном локальном окружении: 19 установленных версий платформы 1С
(8.3.19 → 8.5.1), Python 3.12.10, SQLite 3.49.1 (FTS5 + trigram в stdlib), Windows 10.
Индекс собирался **фактическим кодом `server.py`**, а не эмуляцией; там, где это отмечено
явно, приведены также замеры дополнительного исследования пяти технологических направлений
(FTS5/морфология, сегментация идентификаторов, fuzzy, семантика, контракт MCP/версионность/
лицензии) с последующей адверсариальной проверкой утверждений и финальной критикой
результата. Всё, что не удалось измерить напрямую, помечено как **ОЦЕНКА**.

---

## 1. Резюме

1. **Поиск работает на четверть.** На golden-set из 12 запросов текущая реализация даёт
   recall@5 = 3/12 (0.25), MRR = 0.250. Находятся только точные совпадения по имени.
2. **65% данных не попадает в индекс.** Опечатка в коде (`category[:-1]` от `"properties"`
   даёт тип `"propertie"`, а не `"property"`) исключает 13 943 свойства из 21 594 членов дерева.
   Секция «Параметры» пуста у 100% элементов из-за неверного regex-лукахеда. 697 событий
   отбрасываются полностью.
3. **Репозиторий не запускается на свежей установке.** `requirements.txt` требует
   `mcp>=1.0.0`; актуальная версия на PyPI — 2.0.0, которая убрала API декораторов
   `@app.list_tools()/@app.call_tool()`, использованное в `server.py`. Это не проблема
   поиска — это блокирующий баг P0.
4. **`.hbk` — не 7z-архив**, а контейнер формата 1Cv8 (проверено на 15 версиях), внутри
   которого лежит обычный ZIP (Deflate). Внешний `7z.exe` и распаковка 177 МБ на диск не
   нужны в принципе — задача решается ~40 строками на stdlib без единой новой зависимости.
5. **Реальный размер корпуса — ~26 тыс. страниц справки, а не 40–120 тыс.**, как
   предполагалось изначально. Это меняет расчёты по fuzzy- и векторному слоям на порядок
   в сторону упрощения: brute-force не требует ANN-библиотек, а полный скан по всем именам
   укладывается в доли миллисекунды.
6. **Главный результат аудита — количественная аблация.** Сегментация идентификаторов сама
   по себе почти не влияет на естественно-языковой поиск (ΔMRR ≈ +0.01…+0.02 на разных
   выборках). Курируемая таблица алиасов на **8 строк** закрывает обе задачи, ради которых
   в исходном ТЗ предполагались векторные эмбеддинги (135 МБ модели, сужение Python до ≥3.11,
   обход лимита PyPI в 100 МБ). Семантический слой спроектирован полностью (раздел 6.4), но
   включается только если превзойдёт связку «алиасы + морфология» на расширенном наборе проб.
7. **Источник справки богаче модели данных.** Помимо `shcntx_ru.hbk`, рядом лежат
   `shcntx_root.hbk` (полное английское зеркало, те же 52 807 путей), `shquery_ru.hbk` (язык
   запросов, 105 страниц) и `shlang_ru.hbk` (операторы, препроцессор, аннотации) — ничего из
   этого не читается. 26 из 104 идентификаторов языка запросов совпадают по имени с методами
   глобального контекста BSL (`TrimAll`, `Lower`, `Left`…) — без явного различения языка
   `validate_syntax` может проверить арность SDBL-вызова по правилам BSL и наоборот.

## 2. Карта текущей реализации

Поток данных от `.hbk` до ответа инструмента, с привязкой к коду:

```
main() [server.py:742]
  └─ если нет syntax_tree.json:
       find_and_extract_syntax_hbk() [server.py:224]
         ├─ ищет ТОЛЬКО последнюю версию 1С (version_dirs[-1], break) [server.py:259-261]
         ├─ ищет shcntx_ru.hbk в <версия>/ ПЕРЕД <версия>/bin/ [server.py:267-270]
         │    (реально файл лежит в bin/ — порядок проверки исторически обратный)
         └─ extract_hbk() [server.py:174] → subprocess 7z.exe → extracted_syntax/ (177 МБ на диск)
       build_syntax_index() [server.py:295]
         ├─ parse_st() [server.py:315] — regex по .st (бинарный bracket-формат 1С)
         ├─ parse_html() [server.py:329] — regex-секции по <p class="V8SH_chapter">
         │    └─ extract_section() [server.py:339] — лукахед ломает секцию «Параметры»
         ├─ process_object() [server.py:368] — обходит ctors/methods/properties (НЕ events)
         └─ json.dump() → syntax_tree.json (26.6 МБ на 8.5.1.1150)
  └─ syntax_index.load() [server.py:21] → json.load() + _build_flat_index() [server.py:27]
       (рекурсивный обход; type=="propertie" не проходит фильтр type in ['property'])
  └─ stdio_server() → 4 инструмента:
       search_syntax   → SyntaxIndex.search()      [server.py:108]  точное имя → substring-скан
       get_function_info → SyntaxIndex.get_by_name() [server.py:127] items[0], без адресации владельца
       suggest_completion → SyntaxIndex.suggest_completions() [server.py:135] startswith, без ранжирования
       validate_syntax → re.match(r'(\w+)\s*\(') [server.py:705] только существование имени
```

Ключевой факт о жизненном цикле: сборка индекса — **побочный эффект первого запуска**
(`main()`, [server.py:750-770]), а не отдельная команда — это прямо противоречит цели
«холодный старт < 2 с» и целям задания.

### 4.4 Аблация: что именно даёт прирост (решающий результат аудита)

На выборке из 6 запросов естественного языка пошагово включались слои поверх FTS5:

| Слой | recall@5 | MRR | Δ MRR |
|---|---|---|---|
| A. имя + владелец + описание (без сегментации) | 1/6 | 0.202 | — |
| B. + сегментация идентификаторов | 2/6 | 0.208 | +0.007 |
| C. + глоссарий аббревиатур (`ЛП` → «лишние пробелы слева справа», из описания метода) | 3/6 | 0.375 | +0.167 |
| D. + таблица алиасов намерений, **8 строк** | 5/6 | 0.583 | +0.208 |

Независимая проверка тем же методом на 4 «трудных» запросах из исходного ТЗ (другой скрипт,
другие веса bm25) даёт ту же качественную картину: сегментация меняет ранг `СокрЛП` с #6 на
#6 (без эффекта), `ЧтениеJSON` с #2 на #2 (без эффекта); эвристический штраф за отсутствие
секции «Синтаксис» **улучшает** `СокрЛП` (#6→#2), но **ломает** `ЧтениеJSON` (#2→#125), потому
что у страниц типов (не методов) секции «Синтаксис» нет в принципе — это не одно и то же, что
«редкая» страница. Оба независимых прогона согласны в главном: **сегментация — это фича
автодополнения и поиска по фрагменту идентификатора (`ЛП`, `JSON`), а не рычаг NL-ранжирования**.

Технический разбор двух запросов, которые лексика не решает:

- **`проверить что значение не пустое` → `ЗначениеЗаполнено`**: токена «пуст» в описании метода
  нет вообще. Связь антонимическая («пустое» ↔ «заполнено»); ни стемминг, ни лемматизация её не
  наводят. Прямая ручная глосса `пуст → заполнен` **ухудшает** ранг (заполнен встречается
  в 488 документах не по теме).
- **`отправить письмо` → `ИнтернетПочта`**: описание — «для отправки и получения сообщений
  (писем)». Общих токенов с запросом нет: `отправить`/`отправки`, `письмо`/`писем` — разные
  словоформы, которые суффиксный стеммер Snowball не сведёт из-за беглой согласной. Только
  словарная лемматизация (pymorphy3) действительно сводит оба к «письмо».

Обе задачи, ради которых в исходном ТЗ предполагались векторные эмбеддинги, **закрываются
восемью строками словаря** без единой новой тяжёлой зависимости. Отсюда — решение по разделу 6.4.

### 4.5 Раскладка и fuzzy (замерено отдельно)

| Запрос | До нормализации | После (raскладка + fuzzy + trigram-префильтр) |
|---|---|---|
| `СтрДлинна` (опечатка) | 0 результатов | **pos=1**, score 0.94 |
| `Cnhlkbyf` (раскладка ЙЦУКЕН→QWERTY) | 0 результатов | **pos=1**, после транслитерации score 1.0 |
| `StrLen`, `ReadJSON`, `Structure` (настоящая латиница) | — | транслитерация НЕ применяется (эвристика: точного совпадения транслитерации нет → не раскладка) |

Латентность: trigram-префильтр сокращает кандидатов до ~400 из 23 764 уникальных имён,
fuzzy-скоринг — 8.4 мс; без префильтра полный скан — 266 мс. При реальном размере корпуса
(~10 480 уникальных имён, раздел 5.1) один проход `rapidfuzz.process.extract` без всякого
префильтра укладывается в единицы миллисекунд — см. раздел 6.3.

## 5. Целевая архитектура

### 5.1 Реальный размер корпуса (важная поправка к постановке задачи)

Изначальное ТЗ предполагало 40 000–120 000 индексируемых элементов. Измерено на 8.5.1.1150
(независимо — собственным разбором контейнера `.hbk` и вторым разбором через 7z, оба сошлись):

- **25 882 страницы справки** (`.html`), **23 075 .st-файлов** (сигнатуры), 3 850 `__categories__`.
- **22 291 член** (13 943 свойства + 7 206 методов + 697 событий + 445 конструкторов) —
  совпадает с собственным замером из [раздела 4.1](#41-текущая-реализация-фактический-код-платформа-8511150)
  с точностью до событий, которые текущий код не обрабатывает вовсе (21 594 + 697 = 22 291).
- **10 480 уникальных русских имён членов**, 10 477 ru↔en пар (бесплатно из `<h1>` и `.st`).

Это на порядок меньше, чем предполагалось, и меняет решения по fuzzy и векторам:
полный скан по 10 480 именам, а не по 100 000, укладывается в доли миллисекунды даже без
префильтра — экономия на архитектуре, а не костыль.

### 5.2 Мультиверсионность: один union-индекс, а не индекс на версию

15 из 19 версий на машине несут `.hbk`; 4 — тонкий клиент без него вовсе. Диапазон
8.3.19 → 8.5.1 (6 версий с шагом) даёт **+2600 добавленных / −340 удалённых** страниц
относительно самой старой версии, union по 6 версиям = 26 488 страниц — **всего на 2.3%
больше**, чем в одной новейшей версии, потому что подавляющее большинство путей общие.
Отдельный `.db`-файл на версию обошёлся бы в ~15 × 64 МБ ≈ 966 МБ и 15 отдельных сборок;
**один union-индекс с таблицей присутствия по версиям — ~66 МБ**. Аналогично для векторов:
26 488 × 384 × 4 байта = 40.7 МБ на union, а не 15 копий по 61–184 МБ.

Дедупликация по пути внутри `FileStorage` (устойчив на всём диапазоне — 23 282 общих пути
между 8.3.19 и 8.5.1) плюс хэш содержимого сигнатуры.

### 5.3 Формат `.hbk`: контейнер 1Cv8, не 7z

Заголовок файла — `FF FF FF 7F 00 02 00 00 13 00 00 00 …` — это контейнер 1Cv8 (magic
`0x7FFFFFFF`, `page_size=512`, `storage_ver=19`), а не 7z (`37 7A BC AF 27 1C`). Сам 7-Zip
успевает открыть его лишь эвристикой (`Type = zip`, `Offset = 1656`, «There are data after
the end of archive»). Внутри контейнера — 7 именованных элементов
(`Book, FileStorage, IndexMainData, IndexPackBlock, MainData, PackBlock, PackLookup`);
`FileStorage` — корректный ZIP (Deflate), который открывается **stdlib `zipfile`** после
извлечения из блочной цепочки контейнера. Проверено на 15 версиях платформы: количество
членов в `FileStorage` совпадает с выдачей 7z (52 807 для `shcntx_ru.hbk` 8.5.1.1150).

Побочная находка: `IndexPackBlock` (8.8 МБ) — собственный предпостроенный полнотекстовый
индекс 1С в непубличном формате; трогать не стоит (см. открытые вопросы), но `PackBlock`
(TOC, дерево страниц с флагами доступности и версией «с какой доступен») — структурированные
метаданные, которые стоит использовать вместо текстового парсинга «Доступен, начиная с
версии X» из HTML.

### 5.4 Языковой дискриминатор: BSL vs SDBL

26 из 104 идентификаторов языка запросов (`shquery_ru.hbk`) совпадают по имени с методами
глобального контекста BSL: `TrimAll`/`СокрЛП`, `StrFind`/`СтрНайти`, `Lower`/`НРег`,
`Upper`/`ВРег`, `Left`/`Лев`, `Right`/`Прав`, `Int`/`Цел`, `Round`/`Окр`, тригонометрия и др.
— у каждой пары разный синтаксис, разная арность, разная доступность. Без колонки
`language ∈ {bsl, sdbl}` точное совпадение по имени становится неоднозначным для самых
частых функций, а `validate_syntax` может свалиться в подмену правил одного языка другим.

### 5.5 Почему SQLite+FTS5, а не JSON/pickle/чистый Python — замер, а не по умолчанию

Важная поправка к мотивировке: SQLite выбран **не ради скорости холодного старта** — в
разделе 4.1 текущий JSON (26.6 МБ) уже грузится за 167 мс, порог в 2 с не нарушен и без
SQLite. Аргумент в пользу SQLite — встроенное ранжирование, фильтры и таблица присутствия
по версиям без необходимости писать и сопровождать их самостоятельно. Ниже — прямое
сравнение на реальных 24 972 элементах справки (не синтетика).

| Вариант | Размер | Холодный старт | Точное имя | Полнотекст | Резидентная память |
|---|---|---|---|---|---|
| JSON-дерево (как сейчас) | 26.6 МБ | 167 мс | — (только dict) | нет | 117 МБ |
| JSON плоский список | 23.3 МБ | 119 мс | 0.0002 мс | нет | 93 МБ |
| pickle (protocol 5) | 20.9 МБ | 81 мс | 0.0002 мс | нет | 66 МБ |
| marshal | 22.1 МБ | 88 мс | 0.0002 мс | нет | 68 МБ |
| SQLite без FTS | 19.4 МБ | 1 мс | 0.069 мс | 22.5 мс (`LIKE`, полный скан) | ~8 МБ (кэш страниц) |
| **SQLite + FTS5** | 26.3 МБ | 10 мс | 0.069 мс | **7.5 мс** (bm25) | ~8 МБ |
| + `prefix='2 3 4'` на именах | 31.1 МБ | — | — | 0.6 мс (автодополнение) | — |
| + `trigram` на именах | 30.1 МБ | — | — | 0.1 мс (подстрока, мин. 3 симв.) | — |
| Чистый Python (инвертированный индекс + BM25) | 4.8 МБ индекс + 20.9 МБ записи = 25.7 МБ | 68+81 мс | 0.0002 мс | **1.6 мс** | ~98 МБ |

`pickle`/`marshal` отклонены как формат поставки независимо от скорости: `pickle`
небезопасен при недоверенном источнике, `marshal` официально не гарантирует
совместимость между версиями Python. `SQLite без FTS` — `LIKE` даёt только полный скан
без ранжирования, то есть не решает P0-1.

**Чистый Python на инвертированном индексе — единственный по-настоящему конкурентный
вариант**: он быстрее по запросу (1.6 мс против 7.5) и не требует зависимостей вовсе. Но
резидентно занимает ~98 МБ против ~8 МБ у SQLite, потому что структура целиком лежит в
памяти процесса, тогда как SQLite подгружает только горячие страницы — для
долгоживущего stdio-сервера, который клиент вправе поднять в нескольких экземплярах,
это решающий аргумент. Кроме того, `k1`/`b` в BM25 у FTS5 зашиты намертво (1.2/0.75) —
у собственной реализации они настраиваемы, и это единственное объективное преимущество
самодельного варианта по качеству ранжирования, а не по инфраструктуре.

Рассмотренные и отклонённые внешние движки: `DuckDB` (MIT, есть FTS-расширение, но
избыточен для 26 тыс. строк и слабее FTS5 по зрелости), `tantivy-py` (MIT, ~4 МБ, второй
движок хранения без измеримого выигрыша при таком N), `Whoosh`/`whoosh-reloaded` (BSD,
апстрим заброшен, на порядок медленнее FTS5), `Xapian` (**GPL-2.0** — несовместим с
MIT-проектом), `PyLucene` (не ставится через pip — нужен JDK+JCC).

**Контрольная проверка, вскрывшая отдельный риск**: при прямом сравнении движков на
запросе `"как обрезать пробелы в строке"` с рассинхронизированной нормализацией (запрос
стеммирован, индекс — нет) выдача обоих движков мгновенно разваливается — `СокрЛП` не
находится ни в SQLite, ни в чистом Python. После выравнивания нормализации (одна и та же
функция токенизации применена и к документам, и к запросу) `текущая дата` → `ТекущаяДата`
встаёт на 1-е место, `прочитать json` → `ПрочитатьJSON` на 2-е — но `СокрЛП` всё равно не
находится, потому что в описании метода буквально «отсекает», а не «обрезает». Это
подтверждает наблюдение раздела 4.4 независимо от выбора хранилища: **движок — не то,
что решает качество поиска; решает глоссарий аббревиатур и таблица алиасов**. Отдельно
это означает, что контракт нормализации (раздел 8, «дороже всего исправлять постфактум»)
должен быть выражен одной переиспользуемой функцией, применяемой и при сборке индекса, и
при обработке запроса, — а не продублирован в двух местах, как в этом контрольном прогоне.

**Выбор**: SQLite + FTS5 — компромисс, а не безусловный победитель по скорости. Он
принят потому, что закрывает P0-1 (ранжирование), P0-5 (таблица присутствия по версиям в
одном файле) и не требует держать резидентно ~100 МБ Python-структур в долгоживущем
процессе — ценой на порядок большего разброса в качестве, целиком зависящего от
глоссария и алиасов, а не от самого движка.

Векторное хранилище (раздел 6.4, условно) SQLite не касается вовсе: `numpy` + `mmap` без
ANN-библиотеки — обоснование там же.

### 5.6 Схема хранения

Один SQLite-файл, union-индекс по всем версиям + таблица присутствия:

```sql
-- ========== схема: index.sqlite, один файл на все версии платформы ==========
CREATE TABLE schema_meta(index_schema_version INTEGER NOT NULL);  -- отказ загрузки при мисматче

CREATE TABLE platform(
  platform_id   INTEGER PRIMARY KEY,
  version       TEXT NOT NULL,             -- '8.5.1.1150'
  vkey          TEXT NOT NULL,             -- '00008.00005.00001.01150' — сортируется как TEXT
  install_path  TEXT NOT NULL,
  hbk_sha256    TEXT NOT NULL,             -- дедуп идентичных сборок (8.3.27.1719 == .1786)
  lang          TEXT NOT NULL,             -- 'ru' | 'root' (английское зеркало)
  built_at      TEXT NOT NULL,
  UNIQUE(hbk_sha256, lang));

-- один канонический элемент на весь диапазон версий, НЕ копия на версию
CREATE TABLE entry(
  entry_id    INTEGER PRIMARY KEY,
  fqn         TEXT NOT NULL,               -- 'Массив.Количество' | 'global.СокрЛП'
  language    TEXT NOT NULL DEFAULT 'bsl', -- 'bsl' | 'sdbl'  — см. 5.4
  kind        TEXT NOT NULL,               -- object|method|property|event|ctor|table
  owner_id    INTEGER REFERENCES entry(entry_id),
  name_ru     TEXT, name_en TEXT,
  name_tokens TEXT,                        -- сегментация PascalCase, см. раздел 6.1
  UNIQUE(fqn, language));

CREATE TABLE entry_version(                 -- присутствие + сигнатура по версии
  entry_id    INTEGER NOT NULL REFERENCES entry(entry_id),
  platform_id INTEGER NOT NULL REFERENCES platform(platform_id),
  sig_hash    TEXT NOT NULL,               -- хэш(signature|params|return) — детектит "изменилось"
  page_path   TEXT NOT NULL,
  min_arity INTEGER, max_arity INTEGER,
  PRIMARY KEY(entry_id, platform_id)) WITHOUT ROWID;

CREATE TABLE detail(                        -- payload хранится ОДИН раз на уникальный sig_hash
  sig_hash TEXT PRIMARY KEY, signature TEXT, params_json TEXT,
  return_type TEXT, description TEXT, example TEXT, availability TEXT);

CREATE TABLE alias(                         -- курируемая таблица намерений, раздел 4.4
  phrase TEXT NOT NULL, target_fqn TEXT NOT NULL);

-- лексика: ДВЕ FTS5-таблицы, не одна — префиксный индекс дорог и не нужен на описаниях
CREATE VIRTUAL TABLE fts_name USING fts5(
  name_ru, name_en, name_tokens,
  content='entry', content_rowid='entry_id',
  tokenize="unicode61 remove_diacritics 2", prefix='2 3 4');   -- suggest_completion

CREATE VIRTUAL TABLE fts_doc USING fts5(
  name_ru, name_en, name_tokens, signature, descr, descr_stem,
  content='entry', content_rowid='entry_id',
  tokenize="unicode61 remove_diacritics 2");                   -- search_syntax, без prefix
```

Почему не contentless-таблицы: `snippet()`/`highlight()` возвращают `NULL` на contentless
FTS5 (проверено), а обычную таблицу `entry`/`detail` всё равно нужно держать для выдачи
деталей — «экономия» contentless в этом случае мнимая.

Векторное хранилище (если раздел 6.4 подтвердится замером): `numpy`-массив `float32`,
`mmap`, без ANN-библиотеки — обоснование в 6.4.

### 5.7 Конвейер запроса: строгие уровни, не сумма скоров

```
T0  точное совпадение по name/fqn (с учётом language)         — не может быть переранжировано
T1  точная строка по производному ключу (сегменты, ё→е,        небольшой фиксированный штраф
    гомоглиф-скелет, транслитерация раскладки)
T2  автодополнение по префиксу (fts_name, prefix='2 3 4')
T3  fuzzy (rapidfuzz, score_cutoff=85) + OSA-гейт по абсолютному числу правок
T4  bm25 по fts_doc (OR как основной проход, AND — как уточнение) + alias-таблица
T5  семантика (если включена, раздел 6.4) — сливается с T3/T4 через RRF
```

Разные типы скоров (0–100 у fuzzy, неограниченный bm25, косинус у эмбеддингов) **никогда не
складываются напрямую** — это была внутренняя нестыковка черновых рекомендаций из
исследования, явно исправленная здесь: RRF применяется только для слияния T3–T5, а T0–T2
остаются жёсткими уровнями, которые ничто не может подвинуть вниз.

## 6. Решения по пяти P0-проблемам

### 6.1 P0-1: Поиск только по именам

**Диагноз**: `flat_index` — это словарь `имя → items`; описание, параметры, владелец нигде
не участвуют в поиске ([server.py:27-106](../server.py#L27)).

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Индексировать описание/параметры/владельца в FTS5 (раздел 5.6) | 0 новых зависимостей, bm25 из коробки | Требует структурного HTML-парсинга вместо regex | ✅ выбрано |
| Оставить плоский словарь, добавить только substring по описанию | Минимум изменений | Тот же класс багов (ранжирование, `break`), не решает NL-запросы | отклонено |

Дополнительно: сегментация PascalCase-идентификаторов в колонку `name_tokens` (см. код в
разделе 8) — измеренный вклад в NL-ранжирование мал (ΔMRR ≈ +0.01), но необходим для
автодополнения по фрагменту (`ЛП`, `JSON`) и для адресации `Объект.Метод` через FQN.

**Риск**: без структурного парсинга (lxml) параметры продолжат теряться так же, как сейчас
регексом — 9 794 из 9 800 блоков `<div class="V8SH_rubric">` содержат незакрытый `<p>`, и
тип+описание параметра лежат в *tail*-тексте `div`, а не внутри него. Regex этого не может
выразить принципиально, не как временный баг, а как ограничение метода.

### 6.2 P0-2: Нет полнотекстового поиска

**Выбор: stdlib `sqlite3` + FTS5**, без дополнительных зависимостей.

| Вариант | Install size | Лицензия | Вердикт |
|---|---|---|---|
| **stdlib `sqlite3` + FTS5** (`unicode61 remove_diacritics 2`) | 0 МБ | public domain / PSF-2.0 | ✅ выбрано — FTS5 подтверждён в CPython 3.12.10/Windows, Debian/Ubuntu/conda-forge, python-build-standalone (`uv`) |
| `tantivy-py` (Rust, Lucene-класс) | ~4 МБ | MIT | отклонено — не даёт измеримого выигрыша при 10 480 именах, второй движок хранения |
| Whoosh / Xapian / PyLucene | 0.5–150+ МБ | BSD / **GPL-2.0** / Apache-2.0+JVM | отклонены — GPL (Xapian), непригодный packaging (PyLucene требует JVM+JDK), устаревший чистый Python (Whoosh) |

Морфология — «отдельная стеммированная колонка», не кастомный токенайзер: регистрация
Python-токенайзера FTS5 через stdlib `sqlite3` **невозможна принципиально** — FTS5 отдаёт
свой API только через `sqlite3_bind_pointer(..., "fts5_api_ptr")`, которого у stdlib-модуля
нет (доступно только через APSW). Поэтому:

| Слой морфологии | Install size | Что решает | Куда |
|---|---|---|---|
| `snowballstemmer` (BSD-3, чистый Python, 104 КБ) | 0.1 МБ | Суффиксный стемминг ru/en | база |
| `PyStemmer` (C-обёртка Snowball, MIT+BSD) | 0.2–0.8 МБ | Ускоряет сборку индекса с минут до секунд | `[fast-build]`, опционально |
| `pymorphy3` + словари (MIT, данные CC BY-SA) | 8.6 МБ | Настоящая лемматизация — снимает часть проблем со словоформами (`письмо`/`писем`) | `[morphology]` |

Русский `unicode61` не сворачивает `ё→е` ни при каком значении `remove_diacritics`
(проверено: `fts5vocab` хранит `ёлка`, `счёт` отдельно от `елка`, `счет`) — это делается
приложением на этапе индексации и запроса, а не токенайзером.

### 6.3 P0-3: Нет fuzzy-поиска

**Выбор: `rapidfuzz`, единственная новая зависимость** (MIT, 1.5 МБ Windows / 3.1 МБ Linux,
без обязательных транзитивных зависимостей).

При реальном размере корпуса (10 480 уникальных имён, не 100 000) полный скан
`process.extract(scorer=fuzz.ratio, score_cutoff=85)` укладывается в единицы миллисекунд —
**никакой префильтр (SymSpell, BK-дерево, trigram) не нужен и не окупается**:

| Вариант | Экономия vs полный скан | Цена | Вердикт |
|---|---|---|---|
| Полный скан `rapidfuzz` по всем именам | — (база сравнения) | 0 доп. затрат | ✅ выбрано |
| `symspellpy` (symmetric delete) | Экономит проход, которого некому дорого стоить | 1.3 с build + 33 МБ RAM на 100k синтетике; на реальных 10k ещё менее оправдано | отклонено |
| BK-дерево | То же | Расстояние Дамерау-Левенштейна не метрика ⇒ фильтрация либо некорректна, либо теряет транспозиции | отклонено |
| FTS5 trigram как префильтр | То же | Подстроки короче 3 символов не матчатся в принципе (`ЛП` не найти триграммой) — сегментация решает это надёжнее | отклонено как префильтр; используется отдельно для поиска по фрагменту |

Обязательные детали, подтверждённые расчётом по замкнутой формуле `ratio = 100(1-k/n)`:
`score_cutoff=85` пропускает любую однобуквенную опечатку при длине имени ≥7 символов и
отсекает реальные похожие-но-разные имена (`СокрЛ`/`СокрП` = 80.0, `ВРег`/`НРег` = 75.0).
Для имён короче 7 символов однобуквенная опечатка неотличима от другого реального имени —
fuzzy для них отключается, разрешены только точное совпадение, префикс и алиасы.

Раскладка ЙЦУКЕН↔QWERTY — таблица на 94 ключа, применяется только при одновременном
выполнении всех условий: нет точного/префиксного совпадения; строка целиком в одном алфавите;
длина ≥5; сама транслитерация после этого даёт точное или fuzzy-совпадение. Замерено: при
таких условиях `StrLen`/`ReadJSON`/`Structure` транслитерации не подвергаются (это реальные
латинские имена), а `Cnhlkbyf`/`Pyfxtybtpfgjkytyj` корректно превращаются в `СтрДлина`/
`Значениезаполнено`.

Точное совпадение **всегда** побеждает fuzzy — обеспечивается структурой уровней (T0 vs T3
в разделе 5.6), а не весами: суммировать 0–100-балльный fuzzy-скор с неограниченным bm25
нельзя в принципе — это была внутренняя нестыковка чернового исследования, исправленная
здесь строгой层аментацией уровней.

### 6.4 P0-4: Нет semantic/vector-поиска

**Спроектировано полностью; решение о включении — по замеру, критерий задан явно (раздел
8, этап 5).** Причина отложенного включения — раздел 4.4: обе цели, названные в исходном
ТЗ («отправить письмо», «проверить что значение не пустое»), закрылись 8-строчной таблицей
алиасов без единой новой зависимости.

**Модель** (если понадобится): `intfloat/multilingual-e5-small`, MIT, официальный
предквантованный ONNX (`model_qint8_avx512_vnni.onnx`, 118.3 МБ) — единственная
компактная модель с хорошим русским качеством (encodechka 0.742, лучшая среди моделей
<500 МБ) и асимметричным обучением `query:`/`passage:`, ровно под задачу «короткий запрос
→ описание метода». **Полный размер комплекта — 135.4 МБ** (модель 118.3 + токенайзер
`tokenizer.json` 17.1 МБ, что часто упускается при подсчёте). `deepvk/USER2-small`
(34 М параметров, Apache-2.0, MTEB-rus retrieval 61.87) — кандидат v2, если сделать
собственный ONNX-экспорт: даёт Matryoshka-усечение до 128 измерений и втрое меньший файл
векторов.

**Рантайм**: `onnxruntime` + `tokenizers` + `numpy`, без `sentence-transformers`
(`torch` — 122 МБ на Windows, `import torch` сам по себе способен съесть весь бюджет
холодного старта в 2 с) и без `fastembed` (нет `multilingual-e5-small` в каталоге,
тянет `pillow`/`mmh3`/`loguru`, по умолчанию кэширует модель в `%TEMP%`, откуда ОС может
её удалить).

**Хранилище векторов**: `numpy`-массив + `mmap`, без ANN-библиотеки. При 26 488 записях
(union-индекс, раздел 5.2) × 384 измерения × 4 байта = 40.7 МБ; один запрос — GEMV на
~30 MFLOP, упирается в пропускную способность памяти, а не в вычисления: **5–10 мс** на
типичном CPU. `hnswlib` не имеет готовых wheel для Windows с конца 2023 (нужен компилятор),
`sqlite-vec` не имеет ANN-индекса вовсе и на этом размере медленнее прямого numpy-скана,
`faiss-cpu`/`usearch` экономят единицы миллисекунд ценой второго индекса и версионирования.
Всё это отклонено как неоправданное усложнение при таком N.

**Слияние**: Reciprocal Rank Fusion, `score(d) = Σ wᵢ/(60 + rankᵢ(d))` — единственная схема,
корректно определённая, когда один из источников возвращает 0 или 1 результат (min-max и
z-score в этом случае делят на ноль). Перед RRF обязателен «короткий замыкатель» на точное
совпадение (T0 из раздела 5.6): RRF с `k=60` намеренно сглаживает разницу между 1-м и 5-м
местом (6% разрыва), и семантический шум иначе способен вытеснить буквальное совпадение
`СокрЛП`.

**Ограничения, из-за которых включение остаётся условным**:
- `onnxruntime` требует Python ≥3.11 (тянет также `protobuf`, `flatbuffers`) — extra
  `.[semantic]` **сужает** поддерживаемую версию Python относительно базовой установки,
  это нужно явно декларировать.
- 135.4 МБ превышает лимит PyPI на файл (100 МБ) — модель нельзя распространять как
  часть wheel; только докачка с GitHub Releases при `build-index --with-embeddings`,
  с фиксацией по sha256 и явным падением при отсутствии сети (без тихого простаивания).
- Квантизация `avx512_vnni` — по данным разработчиков ONNX Runtime, на процессорах без
  AVX-512 VNNI (в том числе часть современных Intel-ноутбуков) может быть медленнее fp32,
  а не быстрее — требует замера на целевом железе перед тем, как делать int8 умолчанием.
- Резидентная память ONNX-сессии (~150–250 МБ, **ОЦЕНКА**) в долгоживущем stdio-процессе,
  который клиент может поднимать в нескольких экземплярах — не учтена ни в одной из смет.

**Критерий включения**: на расширенном наборе из 40+ проб (раздел 9) семантический слой
должен дать прирост MRR сверх связки «алиасы + морфология», иначе он не входит в базовую
поставку продукта, а остаётся опциональным `.[semantic]`.

### 6.5 P0-5: Нет поддержки нескольких версий платформы

**Диагноз** и **решение** покрыты в разделе 5.2 (union-индекс) и 5.3 (обнаружение всех
установок). Ключевые решения:

| Вопрос | Решение | Обоснование |
|---|---|---|
| Обнаружение версий | Скан известных путей (`C:\Program Files\1cv8`, `/opt/1cv8/<arch>/`, `/opt/1C/v8.3/<arch>/`), НЕ реестр | На этой машине `HKLM\SOFTWARE\1C` не существует вовсе при 19 установках; ветка `Uninstall` покрывает только 13 из 19 |
| Версии без `.hbk` | Требовать `bin/shcntx_*.hbk` для допуска версии в список | 4 из 19 версий — тонкий клиент, `.hbk` физически нет |
| Сортировка версий | `tuple(int(p) for p in ver.split('.'))`, а не строка/float | Текущий код падает на любом нечисловом сегменте без защиты |
| Хранение | Один union-индекс + таблица присутствия по `platform_id` (раздел 5.6) | 15 отдельных индексов ≈ 966 МБ и 15 отдельных сборок против ~66 МБ union |
| Дедупликация сборок | SHA-256 `.hbk` | `8.3.27.1719` и `8.3.27.1786` физически идентичны — не пересобирать |
| «Доступно начиная с версии» | Брать из `PackBlock`/`__categories__` (структурированные метаданные 1С), не парсить текст HTML | 98% страниц несут эту информацию текстом; структурные метаданные надёжнее регекса |
| Diff между версиями | SQL-запрос по `entry_version` (LEFT JOIN двух `platform_id`) — раздел 8 | Не требует хранить два полных индекса одновременно |

## 7. Новый контракт инструментов MCP

Имена всех четырёх существующих инструментов сохраняются без изменений; расширение — только
необязательными параметрами с обратно совместимыми значениями по умолчанию (это соответствует
и духу задания, и решению пользователя работать в своём форке без диктата чужой обратной
совместимости, но с сохранением привычного интерфейса).

### `search_syntax`

```jsonc
// input (новые поля — необязательные; старые query/limit не изменились)
{
  "query": "СокрЛП",
  "limit": 10,
  "offset": 0,               // NEW — пагинация
  "kind": null,               // NEW — object|method|property|event|ctor
  "owner": null,               // NEW — сузить до конкретного объекта-владельца
  "language": "bsl",           // NEW — bsl|sdbl, раздел 5.4
  "platform": null,            // NEW — версия платформы; по умолчанию новейшая установленная
  "detail": "brief"            // NEW — brief|full, управляет объёмом ответа
}
```

```jsonc
// output — структурированный JSON вместо склеенной строки; экономия токенов через detail
{
  "query": "СокрЛП", "platform": "8.5.1.1150", "total": 3, "returned": 3,
  "offset": 0, "next_offset": null,
  "results": [
    {"fqn": "global.СокрЛП", "kind": "method", "language": "bsl",
     "name_ru": "СокрЛП", "name_en": "TrimAll",
     "signature": "СокрЛП(<Строка>)", "score": 1.0, "tier": "exact",
     "since": "8.0"}
  ]
}
```

### `get_function_info` → добавлены `owner`, `platform`, `language`; при коллизии без `owner`
возвращает **список кандидатов с их владельцами**, а не произвольный `items[0]`.

### `suggest_completion` → добавлен `kind`; результаты ранжированы по `fts_name`
(`prefix='2 3 4'`) вместо порядка обхода файловой системы.

### `validate_syntax` → расширенный, честный результат вместо бинарного вердикта:

```jsonc
{
  "ok": false,
  "checks": [
    {"code": "arity_mismatch", "severity": "error",
     "expected": "СтрДлина(<Строка>)", "note": "передано 5 аргументов, ожидается 1"}
  ],
  "undecidable": ["тип получателя перед .Записать() не выводится из исходного текста"]
}
```

Честно проверяется: существование имени в данной версии платформы; арность и опциональность
параметров по разобранной сигнатуре; принадлежность глобальному контексту vs метод объекта;
членство в перечислении; однократное разрешение точечного вызова, если тип получателя явно
указан в исходном тексте (`Новый Массив`). Не проверяется и не заявляется: полный вывод типов,
поток управления, объекты метаданных конфигурации. Если потребуется переименование —
регистрируется второй инструмент (`check_api_usage`), старое имя остаётся с пометкой
`DEPRECATED` в описании и делегирует тому же обработчику не менее двух минорных релизов.

### Новые инструменты

- **`list_versions`** — список версий платформы, для которых собран индекс, с датой сборки,
  хэшем `.hbk` и числом элементов.
- **`get_by_fqn`** — точное разрешение `Объект.Метод` (закрывает P0-1, дизамбигуация
  коллизий).

Все инструменты помечаются `readOnlyHint: true`, `destructiveHint: false`,
`openWorldHint: false` (сервер не обращается в сеть на этапе запросов) — сервер строго
локальный и доступен для чтения без подтверждений в клиентах, которые уважают эти хинты.

## 9. Метрики качества

- **golden-set** — репозиторная копия 12 запросов из раздела 4.2 плюс расширение минимум до
  40 проб, включая ≥10 проб по языку запросов (сейчас recall = 0 под любой из рассмотренных
  архитектур) и явные кейсы на антонимию/словоформы (раздел 4.4) — критерий включения
  семантического слоя считается именно на этом расширенном наборе, не на исходных 12.
- **recall@5** и **MRR** — 25 строк на чистом Python поверх выдачи `search_syntax`, без
  внешних зависимостей (`ranx`/`pytrec_eval` тянут `numpy`/`numba` непропорционально задаче).
- **Латентность** — p50/p90 по каждому уровню конвейера (раздел 5.7) отдельно, чтобы
  регрессия в одном уровне не терялась в сумме.
- **CI**: golden-set гоняется на синтетическом `.hbk`-фикстуре (собственный формат контейнера
  воспроизводим в ~40 строк), потому что реальный `.hbk` — проприетарные данные 1С и не может
  распространяться в публичном репозитории (раздел про лицензии ниже). Прогон на реальном
  `.hbk` — отдельный, локальный, опциональный джоб для тех, у кого установлена платформа.
- Матрица CI: `ubuntu-latest` + `windows-latest` × поддерживаемые версии Python — различия в
  порядке `os.listdir`, кодировках и разделителях путей иначе остаются непротестированными.

**Лицензионная позиция** (не юридическая консультация, а практика сопоставимых проектов):
`shcntx_ru.hbk` — сопроводительные материалы 1С, EULA явно резервирует «любые сопроводительные
материалы в печатном или электронном виде» и запрещает распространение компонентов продукта
без письменного разрешения. Ни один из проверенных сравнимых проектов (`bsl-context`,
`bsl-help-toc-parser`, `otymko/bsl-context-collector`, `alkoleft/mcp-bsl-platform-context`)
не публикует извлечённый контент справки — все строятся из локальной установки пользователя.
Политика этого проекта: индекс **всегда собирается локально**; в репозиторий и релизы попадает
только код, схема, синтетические фикстуры для тестов и собственные формулировки golden-set
запросов (не описания из справки).

### 9.1 Решение по Этапу 5 (семантика): нет, по измерению

Открытый вопрос №1 закрыт: golden-set расширен с 12 до **42** запросов
(`tests/golden_set.py`) — 14 новых NL-запросов на BSL и 16 на языке запросов
(SDBL), последние явно проверяются с `language='sdbl'`. Критерий этапа 5 требует
превзойти по MRR связку «алиасы + морфология» — на момент проверки эта связка
**не существовала полностью**: этапы 1-4 закрыли разрыв сегментацией и алиасами
(раздел 4.4), но не стеммингом, который раздел 6.2 относит к тому же решению.
Прежде чем сравнивать с эмбеддингами, связку пришлось сначала честно собрать:

| Шаг | recall@5 | MRR | Δ MRR |
|---|---|---|---|
| Алиасы + сегментация (было на конец этапа 4) | 31/42 (0.738) | 0.609 | — |
| + стемминг Snowball ru/en (`morphology.py`) | 34/42 (0.810) | 0.713 | +0.104 |
| + 3 точечных алиаса на измеренные остатки | **37/42 (0.881)** | **0.785** | +0.072 |

Попутно найдены и исправлены два реальных бага, не связанных со стеммингом
напрямую, но обнаруженных только при добавлении `language`-фильтрации на
расширенном наборе:
- в уровне T4 (bm25) `kind`/`owner`/`language` фильтровались в Python **после**
  `LIMIT`, из-за чего редкая целевая запись (например единственная запись SDBL
  среди тысяч BSL-совпадений на общеупотребимые слова) обрезалась раньше, чем до
  неё доходил фильтр — тот же класс ошибки, что уже был найден и исправлен в
  `suggest_completions` на этапе 2. Запрос «количество записей в запросе» с
  `language='sdbl'` до фикса возвращал 0 результатов при существующей записи;
- уровень T3 (fuzzy) дедуплицировал совпадения через `set()`, чей порядок обхода
  строк рандомизирован между процессами Python (хеш-сид) — из-за этого MRR не
  совпадал между повторными запусками одного и того же теста на одних и тех же
  данных. Исправлено дедупликацией по лучшему счёту с детерминированной
  сортировкой; заодно результаты fuzzy стали ранжироваться по релевантности, а не
  в произвольном порядке.

**Итог**: без единой новой зависимости, без сужения поддерживаемой версии Python,
без загрузки 135 МБ модели recall@5 вырос с 0.738 до 0.881 на 42 пробах. Из
оставшихся 5 расхождений одно — известное ограничение самого теста («Стр»
проверяет ранжирование `suggest_completion`, а не `search_syntax`, раздел 4.2), и
четыре — не «не найдено», а «найдено на позиции 6-10» (вопрос донастройки весов
`bm25`, не принципиальная невозможность). Ни один из измеренных остатков не имеет
формы, для которой семантика была бы решением, а лексика — принципиально нет:
это либо более редкая формулировка, которую закрывает ещё один алиас, либо
вопрос ранжирования внутри уже найденного набора. Довод раздела 4.4 («восемь
строк словаря закрывают обе задачи, для которых предполагались эмбеддинги»)
подтвердился на 42 пробах, а не только на исходных 12 — семантический слой
**не внедряется**. Проектные решения раздела 6.4 (выбор модели, рантайма,
хранилища векторов, RRF) остаются в документе как справочный материал на случай,
если будущий, ещё более широкий golden-set вскроет остаток, который не закрывается
алиасом или стеммингом.

### Чтение `.hbk` без внешних зависимостей (контейнер 1Cv8 → `zipfile`)

```python
import io, struct, zipfile

BLOCK = 31  # b"\r\n%08x %08x %08x \r\n"

def _hdr(buf, off):
    h = buf[off:off + BLOCK]
    if len(h) < BLOCK or h[:2] != b"\r\n":
        return None
    a, b, c = h[2:-2].split()
    return int(a, 16), int(b, 16), int(c, 16)          # doc_size, block_size, next_page

def _doc(buf, off):                                     # следуем цепочке блоков
    size, _, _ = _hdr(buf, off)
    out, rem, cur = bytearray(), size, off
    while cur != 0x7FFFFFFF and rem > 0:
        _, bs, nxt = _hdr(buf, cur)
        take = min(bs, rem)
        out += buf[cur + BLOCK: cur + BLOCK + take]
        rem -= take
        cur = nxt
    return bytes(out)

def open_hbk(path):                                      # -> {имя_элемента: bytes}
    raw = open(path, "rb").read()
    root = _doc(raw, 16)
    words = struct.unpack("<%dI" % (len(root) // 4), root)
    elements = {}
    for i in range(0, len(words), 3):                     # (name_addr, data_addr, 0x7FFFFFFF)
        name = _doc(raw, words[i])[20:].decode("utf-16le").rstrip("\x00")
        elements[name] = _doc(raw, words[i + 1])
    return elements

fs = zipfile.ZipFile(io.BytesIO(open_hbk("shcntx_ru.hbk")["FileStorage"]))
# 52 807 членов, все Deflate — совпадает с выдачей 7z; проверено на 15 версиях платформы
```

### Сегментация идентификаторов (~130 тыс. имён/с, без зависимостей)

```python
CYR = set("АБВГДЕЁЖЗИЙКЛМНОПРСТУФХЦЧШЩЪЫЬЭЮЯабвгдеёжзийклмнопрстуфхцчшщъыьэюя")

def _cls(ch):
    if ch.isdigit(): return "D"
    if ch in CYR:    return "CU" if ch.isupper() else "CL"
    if ch.isalpha(): return "LU" if ch.isupper() else "LL"
    return "X"

def _script(k):
    return "C" if k in ("CU", "CL") else ("L" if k in ("LU", "LL") else k)

def segment(name):
    """СокрЛП -> [Сокр, ЛП]; ЧтениеJSON -> [Чтение, JSON]; HTTPRequest -> [HTTP, Request]."""
    if not name:
        return []
    k = [_cls(c) for c in name]
    out, cur = [], name[0]
    for i in range(1, len(name)):
        p, c = k[i - 1], k[i]
        if c == "X" or p == "X":
            brk = True
        elif p == "D" and c != "D":
            brk = True                                    # 64Строка -> 64|Строка
        elif p != "D" and c == "D":
            brk = False                                    # Base|64 остаётся Base64
        elif _script(p) != _script(c):
            brk = True                                    # ЧтениеJSON, XMLСтрока
        elif p in ("CL", "LL") and c in ("CU", "LU"):
            brk = True                                    # ЗначениеЗаполнено
        elif p in ("CU", "LU") and c in ("CU", "LU") and i + 1 < len(name) and k[i + 1] in ("CL", "LL"):
            brk = True                                    # HTTPRequest -> HTTP|Request
        else:
            brk = False
        if brk:
            out.append(cur); cur = name[i]
        else:
            cur += name[i]
    out.append(cur)
    return [s for s in out if s.isalnum()]
```

### Безопасное построение FTS5 MATCH из произвольного текста пользователя

```python
import re

TOKEN_RE = re.compile(r"[^\W_]+", re.UNICODE)

def build_match(text, mode="OR", prefix_last=True):
    """OR — основной проход (recall), AND — уточнение поверх уже найденного (precision).
    Голая интерполяция текста пользователя в MATCH ловит sqlite3.OperationalError
    на '*', '\"unclosed', 'дата AND', 'СокрЛП()' — все проверено вручную."""
    toks = TOKEN_RE.findall(text.lower().replace("ё", "е"))
    if not toks:
        return None
    q = ['"' + t.replace('"', '""') + '"' for t in toks]
    if prefix_last:
        q[-1] += "*"                                       # звёздочка ВНЕ кавычек
    return f" {mode} ".join(q)
```

### Слияние разнородных источников: RRF с коротким замыкателем на точное совпадение

```python
import collections

def rrf(ranked_lists, weights, k=60):
    """Cormack, Clarke & Buettcher, SIGIR 2009. Единственная схема, определённая,
    когда один из источников вернул 0 или 1 результат — min-max/z-score делят на ноль."""
    out = collections.defaultdict(float)
    for lst, w in zip(ranked_lists, weights):
        for rank, doc_id in enumerate(lst, start=1):        # ранги с 1
            out[doc_id] += w / (k + rank)
    return sorted(out.items(), key=lambda kv: -kv[1])

def search(query, exact_index, lexical, semantic, semantic_ready):
    exact = exact_index.get(query.strip().lower())
    if exact:
        return [exact]                                      # T0 — RRF никогда не видит эту ветку;
                                                              # при k=60 разрыв 1-го и 5-го места —
                                                              # всего 6%, семантика способна вытеснить
                                                              # буквальное совпадение, если его не
                                                              # замкнуть отдельно
    lists, weights = [lexical.search(query, 50)], [1.0]
    if semantic_ready:
        lists.append(semantic.search(query, 50)); weights.append(1.0)
    return rrf(lists, weights)
```
